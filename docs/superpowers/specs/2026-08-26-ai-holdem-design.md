# AI 홀덤 — 설계 스펙

날짜: 2026-08-26
상태: 리뷰 수렴 완료 — 2라운드 교차 모델 리뷰(grok-4.6 + gpt-5.6-sol) 후 수렴 판정(R2 신규 표면 1/24, 파장-과반 + 상태기계급 이월 규칙). 이월 목록은 §14

## 1. 개요

AI와 함께 즐기는 노리밋 텍사스 홀덤. 메인 Claude 세션이 딜러가 되어 게임을 진행하고, AI 플레이어들은 각자 랜덤 페르소나를 부여받은 독립 에이전트로 스폰된다. 게임은 로컬 웹 UI에서 진행되며, 사용자는 브라우저에서 베팅 등 액션을 입력한다. 핸드마다 짧은 코칭 피드백이 쌓이고, 게임이 끝나면(사용자 버스트 = 패배, AI 전원 탈락 = 우승) 전체 핸드 히스토리 기반 종합 리뷰로 실력 향상을 돕는다.

목표: AI와 홀덤을 **즐기면서** 사용자의 실력이 **늘게** 하는 것.

## 2. 확정 결정사항

| 결정 | 내용 |

| 스택 | 무빌드 Node.js, 외부 의존성 0개 — 지속 실행되는 웹 서버 프로세스 1개 + 호출형(단발성) 엔진 CLI 프로세스. 서버→브라우저 SSE, 브라우저→서버 fetch POST |

| 규칙 판정 | 전부 순수 코드(엔진). LLM은 규칙·칩 계산을 하지 않음 |

| UI 언어 | 한국어 |

## 3. 아키텍처

실행 중 참여자는 세 종류다.

```
┌─────────────┐  Bash(engine CLI)   ┌──────────────┐
│ 딜러         │────────────────────▶│ 포커 엔진      │── game/state.json (진실의 원천)
│ (메인 세션)   │                     │ (순수 JS CLI) │── game/hands/hand-NNNN.json
└──┬───────┬──┘                     └──────────────┘
   │       │ SendMessage(상황) / JSON 액션 응답
   │       ▼
   │    ┌────────────────────┐
   │    │ 플레이어 에이전트들     │  (Agent tool로 스폰, 게임 내내 유지)
   │    └────────────────────┘
   │ HTTP POST /api/publish (이벤트·화면 상태)
   ▼
┌─────────────┐   SSE /api/events   ┌──────────────┐
│ 웹 서버       │────────────────────▶│ 브라우저 UI    │
│ (server.js)  │◀────────────────────│ (포커 테이블)   │
└─────────────┘  POST /api/action   └──────────────┘
        ▲ GET /api/wait-action (long-poll)
        └── 딜러가 사용자 액션 대기
```

- **웹 서버**는 게임 로직이 전혀 없는 중계기다: 정적 UI 서빙, 딜러가 게시한 이벤트의 SSE 중계, 사용자 액션 큐잉, 마지막 화면 상태 캐시(`/api/snapshot`, 새로고침 복구용).
- **딜러(메인 세션)**는 오케스트레이터다: 엔진 CLI 호출로 상태 전이, AI 차례면 에이전트에 SendMessage, 사용자 차례면 long-poll 대기, 모든 이벤트를 서버에 게시, 딜러 멘트로 나레이션, 핸드 종료 시 코칭 코멘트 생성.
- **진실의 단일 원천은 `game/state.json`** (엔진만 읽고 쓴다). 딜러 세션 컨텍스트가 요약되거나 서버가 재시작돼도 게임은 상태 파일에서 복원된다.

### 게임 무결성 계약 (단일 writer·원자적 쓰기·락)

- `game/lock.json` = `{serverPid, port, sessionToken, startedAt}` — **웹 서버가 기동 시 원자적으로 작성**한다. 엔진 CLI의 단발 pid는 lock에 기록하지 않는다.
- 불변식: **딜러 세션 1개, 엔진 상태 파일의 writer는 엔진 CLI 1개**. 딜러는 state.json을 직접 읽거나 쓰지 않고 view/legal 명령으로만 조회한다.
- 엔진 CLI의 모든 파일 쓰기는 temp 파일 작성 후 원자적 rename으로 수행한다.
- 커밋 순서: **state.json이 선행 커밋(진실의 원천)**, 핸드 아카이브는 후행 파생. state는 직전 핸드 요약(lastHand)을 보유하며, resume 자가검사에서 아카이브 누락이 발견되면 state에서 재생성한다(roll-forward, 멱등).
- 엔진 CLI의 모든 상태 변경 명령은 mutation lock(락 파일) 임계구역 안에서 읽기→검증→쓰기를 수행한다. 원자적 rename과 함께 동시 CLI 실행의 lost update를 차단한다.
- `init`은 lock이 존재하고 serverPid가 생존이면 거부한다. `--force`는 구 서버에 SIGTERM을 보내고 기존 게임을 폐기한 뒤 새로 시작한다.
- `resume`: 서버가 생존이면 그 서버에 그대로 attach(재기동 없이 상태 재게시부터), 서버가 죽었으면 같은 포트로 재기동 후 진행한다. 딜러 세션의 중복 실행 방어는 단일 사용자 머신 전제로 락으로 강제하지 않는다(엔진 mutation lock이 상태 훼손은 차단) — §14 이월 참고.

### 게임 루프 (딜러 절차)

```
1. 사전 점검 (node 존재, 포트, 기존 게임 유무)
2. engine init (페르소나 랜덤 생성 포함) → 서버 백그라운드 기동 → 브라우저 열기
3. 플레이어 에이전트 스폰 (명명 에이전트, 페르소나 카드 전달)
4. 반복 (게임 종료까지):
   a. engine new-hand  → 블라인드 게시·딜링 이벤트 게시
   b. 핸드 진행 중 반복:
      - engine legal → 다음 행동자 + 가능 액션
      - 사용자 차례: /api/wait-action long-poll (타임아웃 시 재시도, 무한 대기 허용)
      - AI 차례: 해당 에이전트에 상황 전송 → JSON 액션 수신
      - engine apply → 결과 이벤트(스트리트 진행·팟 정산 포함) 게시
   4b 탈출: apply/legal 결과의 handOver=true면 4c로, gameOver=true면 5로 이동한다.
   c. 핸드 종료(아카이브는 엔진이 apply에서 이미 기록): 코칭 코멘트 생성(비공개 정보 제외) 게시,
      버스트 처리(AI면 작별 멘트 후 퇴장, 사용자면 게임 종료), 레벨업 안내
5. 게임 종료: 전체 히스토리 기반 종합 리뷰 생성 → UI 리뷰 화면 게시 → 에이전트 정리
```

딜러 세션이 컨텍스트 요약·중단 후 재진입할 때의 고정 절차: ① lock·서버 liveness 확인(`GET /api/health`; 죽었으면 재기동) → ② `legal` 호출 → ③ 현재 decisionId를 포함한 `view --for user` 재게시 → ④ toAct가 사용자면 wait-action, AI면 에이전트에 상황 요약 전송. decisionId는 같은 결정 지점 (handNo, street, actionIndex)에 대해 **안정적**이다 — apply가 성공하기 전까지 legal을 다시 호출해도 새 id가 생기지 않는다. 사용자 액션의 apply가 거부되면(불법·버전 불일치) 강제 폴드하지 않고, 안내 이벤트 + 최신 legal/view 재게시 후 wait-action으로 재진입한다. 엔진 stdout은 컴팩트하게 유지한다(전체 상태 덤프 금지 — 상태 조회는 view로만).

## 4. 포커 엔진 (`engine/`)

순수 JS, 의존성 0, 상태 파일 기반 CLI. 모든 명령은 JSON을 stdout으로 출력한다.

### 규칙 범위

- 노리밋 텍사스 홀덤, 2~9인, 버튼/SB/BB 로테이션 (헤즈업 특례: 버튼=SB 포함)
- 미니멈 레이즈 규칙 — 언더 레이즈 올인은 베팅을 다시 열지 않는 규칙 포함
- 올인·사이드팟(다중), 스플릿 팟(홀수 칩은 버튼 왼쪽 첫 좌석부터)
- 쇼다운 공개 순서: 마지막 베팅 스트리트의 마지막 공격자부터 시계방향. 마지막 스트리트에 공격(벳/레이즈)이 없었으면 버튼 왼쪽 첫 잔존 좌석부터 시계방향. 승자가 되는 패는 반드시 공개되며, 이미 공개된 패에 지는 패는 머킹(비공개)할 수 있다.
- 올인 후 콜 완료 시 잔여 보드 자동 런아웃
- 블라인드 포스팅 시 스택이 부족하면 남은 칩 전액 올인으로 포스팅한다(사이드팟 규칙이 흡수). 스택 0 좌석은 이미 탈락이므로 포스팅 대상이 아니며, 이 경우에도 `new-hand`는 성공한다.
- 7카드 핸드 평가기 자체 구현 (하이 핸드만, 로우 없음)
- 셔플: `crypto.randomInt` 기반 Fisher-Yates
- 블라인드 스케줄: 25/50 → 50/100 → 75/150 → 100/200 → 150/300 → 200/400 → 300/600 → 400/800 → 500/1000 → 700/1400 → 1000/2000 → 이후 매 레벨 ×1.5 반올림. 앤티 없음
- 통계 집계: 플레이어별 VPIP, PFR, 공격 빈도, 쇼다운 승률, 핸드별 수지

### 액션 스키마와 명령 envelope (계약)

- 액션 enum은 `fold | check | call | raise` 4개다. 올인은 별도 액션이 아니라 `raise`를 maxRaiseTo까지 올리는 것(UI의 "올인" 프리셋 = raise-to maxRaiseTo 단축)이거나, 콜 금액이 스택 이상일 때의 `call`(올인 콜)이다.
- `amount`는 항상 **raise-to (그 스트리트의 내 총 베팅액)**인 정수 칩이며, raise-by(추가분)가 아니다.
- `legal` 반환 형태: `{ok, stateVersion, decisionId, handNo, street, toAct, canCheck, callAmount, canRaise, minRaiseTo, maxRaiseTo, potTotal, handOver, gameOver}`. 언더 레이즈 올인만 가능한 경우는 `minRaiseTo > maxRaiseTo`로 표현되며 이때 유일한 합법 레이즈는 maxRaiseTo(올인)이다.
- 모든 명령의 공통 stdout envelope: 성공 `{ok:true, stateVersion, events:[...], ...명령별 필드}`, 실패 `{ok:false, code, message}`. exit code: 0 성공 / 1 거부(불법 액션 등) / 2 사용법 오류. **실패 시 상태 파일은 무변경임을 엔진이 보장한다.**
- `apply`는 `--expect-version <N>` 옵션을 받는다(딜러는 직전 legal의 stateVersion을 전달). 불일치 시 거부하며, 중복 적용·경합을 값싸게 차단한다.
- 모든 이벤트는 `{seq, visibility, type, ...}` 형태이고 `visibility`는 `public | actor:<playerId> | engine` 3종이다. **딜러는 public 이벤트만 서버에 게시하고, 나레이션도 public 이벤트만 근거로 작성한다** (홀카드·덱 유출 차단).
- `view --for user` 반환 필드(고정): `{handNo, level, levelEvery, blinds, street, board, pots[], seats[](playerId, name, stack, bet, folded, allIn, isButton), toAct, myCards, legal?, gameOver, result?}`. `levelEvery`는 UI가 다음 레벨업까지 남은 핸드를 계산하기 위한 공개 설정값이다(순수 추가 필드). `legal`은 사용자 차례일 때만 포함되며 `legal` 명령과 동일 숫자 + `decisionId`를 담는다 — UI 액션 바는 이것으로 활성화된다.
- 이벤트 type enum(최소): `hand_start, blinds_posted, deal_hole(actor), action, street, showdown, pot_award, level_up, bust, talk, coach, game_over`.
- 핸드 히스토리는 각 결정 지점마다 `{decisionId, street, potTotal, callAmount, minRaiseTo, maxRaiseTo, 공개 보드, 각자 스택}` 스냅샷을 기록한다(redacted 뷰도 보존) — 코칭의 결정 시점 재구성용.

### CLI 명령

| 명령 | 역할 |
|---|---|
| `init --ai <n> [--stack N] [--blinds SB/BB] [--level-every N]` | 게임 생성. 페르소나 랜덤 생성 포함 → `game/state.json`, `game/players.json`. 사용자 좌석의 playerId는 `user`(UI 표기 "나") |
| `new-hand` | 셔플·딜링·블라인드 포스팅·레벨업 판정. 결과 이벤트 배열 반환. 게임이 종료 상태(gameOver)이거나 사용자 스택이 0이면 거부 |
| `legal` | 현재 행동자 + 합법 액션 목록(콜 금액, 레이즈 범위). `handOver`, `gameOver` 포함(게임 종료 시 `result`, `bustedPlayerIds`도 포함) |
| `apply <playerId> <action> [amount]` | 액션 검증·적용. 베팅 라운드 종료 시 다음 스트리트, 쇼다운, 팟 분배까지 자동 진행하고 발생 이벤트 전부 반환. `handOver`, `gameOver` 포함(게임 종료 시 `result`, `bustedPlayerIds`도 포함) |
| `apply <playerId> --force-default` | 무응답 플레이어 강제 처리 (체크 가능하면 체크, 아니면 폴드) |
| `view --for <playerId\|user>` | 해당 관점으로 편집(redact)된 화면 상태. UI 게시는 `--for user` |
| `hand <n> [--redacted]` | 핸드 히스토리 조회. `--redacted`는 사용자 관점에서 공개된 정보만 (핸드별 코칭용) |
| `stats` | 누적 통계 (종합 리뷰용) |
| `end --result abort` | 게임 중단(abort) 마킹 전용. 정상 승패(gameOver)는 `apply`가 정산과 함께 엔진 안에서 원자적으로 판정·기록한다 |

- 불법 액션은 명확한 오류 JSON으로 거부한다. 딜러는 state.json을 직접 수정하지 않는다.
- `game/state.json`에는 덱(미공개 카드)이 포함된다 — **엔진만 읽고 쓰며, 딜러를 포함한 다른 프로세스는 열지 않는다**. `sessionToken`은 init의 stdout과 lock.json으로 전달되고, UI에는 `view` 결과만 게시되므로 노출되지 않는다.
- 핸드 종료 시 엔진이 `game/hands/hand-NNNN.json`(전체 정보 포함)을 기록한다.
- 핸드 정산 후 사용자 스택 0 → 패배 종료. 사용자가 생존하고 AI 전원 스택 0 → 우승 종료. 그 외 계속.

## 5. 웹 서버 (`server/server.js`)

Node 내장 `http`만 사용. 서버는 **127.0.0.1에만 바인딩**하며 포트는 기본 8877 (`--port` 옵션)이다. `init`이 난수 `sessionToken`을 생성해 state에 저장하고, 브라우저는 `/?token=...`으로 접속하며 이후 모든 API 요청에 토큰을 포함한다. 토큰 없는 요청은 거부하고 JSON 바디 크기 상한은 64KB로 둔다.

| 엔드포인트 | 역할 |
|---|---|
| `GET /` 및 정적 파일 | 포커 테이블 UI (`server/public/`) |
| `GET /api/health` | 생존 확인 (토큰 불필요) |
| `GET /api/events` | 브라우저 SSE 구독 (이벤트 스트림) |
| `GET /api/snapshot` | 마지막 게시 상태 (새로고침·재접속 복구) |
| `POST /api/publish` | 딜러가 이벤트 배치 + 화면 상태 게시 → SSE 브로드캐스트 + 스냅샷 갱신 |
| `POST /api/action` | 사용자 액션 `{decisionId, action, amount?}`를 깊이 1 슬롯에 적재(최신 값이 덮어씀) |
| `GET /api/wait-action?timeoutMs=25000` | 딜러 long-poll. 액션 도착 시 즉시 반환, 타임아웃 시 `{timeout:true}` |

서버 기동은 detached(터미널 훅업 없이 nohup/setsid + 출력 파일 리다이렉트)다. 서버는 액션의 합법성을 판단하지 않는다(딜러가 엔진으로 검증). 사용자 액션은 큐가 아니라 깊이 1 슬롯이며, `wait-action`이 소비하면 슬롯을 비운다. `decisionId`는 딜러가 게시한 "내 차례" 상태에 포함된 값이다. 딜러는 decisionId가 현재 결정과 불일치하면 폐기하고 안내 이벤트를 게시한다. UI가 내 차례에만 버튼을 활성화해 1차로 거른다. 딜러는 publish 본문에 단조 증가 `publishId`를 포함하고, 서버는 마지막 publishId를 스냅샷에 저장해 중복 publish에는 기존 revision을 반환한다(멱등). 서버는 publish마다 단조 증가 `revision`을 부여하고 SSE 이벤트 id로 사용한다. **스냅샷 = `{revision, view, 누적 이벤트 로그, 누적 코치 노트}`**이며 매 publish 시 `game/ui-snapshot.json`에 원자적으로 저장한다(서버 재시작 시 복원). 복구를 위한 재게시는 view만 갱신하며 events를 포함하지 않는다(누적 로그 중복 방지). 클라이언트는 ① `GET /api/events?token=...&after=<revision>`으로 먼저 접속 → ② snapshot 로드 → ③ after 기준으로 적용한다. 서버는 누적 로그에서 after 이후 이벤트를 재전송한다(부트스트랩 갭 차단). GET 계열 요청의 토큰은 `?token=` 쿼리로 받는다(EventSource가 커스텀 헤더를 지원하지 않으므로). SSE는 15초 간격 heartbeat 코멘트를 보낸다. `POST /api/action`은 서버가 최신 게시된 decisionId와 불일치하면 409로 거부한다(낡은 요청이 유효 액션을 덮어쓰지 못함). `wait-action`은 `expectDecisionId` 쿼리로 일치하는 액션만 소비한다. 딜러는 재진입·publish 실패 시 health로 생존을 확인하고 죽었으면 재기동한다.

## 6. 플레이어 에이전트

### 페르소나 (init 시 1회 생성(`players.json`), 스폰·resume은 읽기만)

- 페르소나 카드 필드: `name, speech, personality, archetype, bluffFreq, threeBetFreq, tiltProne` (이름은 한국어 이름 풀에서 중복 없이 추첨)
- players.json 계약: `{playerId, seat, name, agentHandle, ...페르소나 필드}`. playerId는 사용자 `user`, AI는 `p1..pN`의 안정 id. `agentHandle`은 스폰 시 에이전트 이름(`player-<playerId>`)이며 SendMessage 대상은 항상 agentHandle이다.
- 아키타입 6종 중 추첨: TAG(타이트 공격형) / LAG(루즈 공격형) / Nit(극단 수비형) / Calling Station(콜쟁이) / Maniac(광인) / Trickster(트랩형)
- 세부 파라미터 변주: 블러프 빈도, 3벳 성향, 틸트 성향 (같은 아키타입도 매번 다르게)
- **스타일은 사용자에게 비공개.** UI에는 이름·아바타만. 종합 리뷰에서 공개된다.

### 통신 프로토콜

딜러 → 에이전트 (매 차례, 자족적 요약):

```
[핸드 12 / 턴] 당신: 서연 (BTN, 스택 4,300) | decisionId: d-12-03
홀카드: A♠ K♦ | 보드: K♥ 7♣ 2♦ 9♠
팟: 850 | 블라인드 50/100
이번 핸드: 민수(UTG) 폴드, 지혜(BB) 체크, … 지혜가 300 벳
가능한 액션: fold / call 300 / raise 600~4300
JSON 한 줄로 응답: {"decisionId":"d-12-03","action":"...","amount":숫자?,"talk":"짧은 한마디(선택)"}
```

에이전트 → 딜러: JSON 한 줄 `{decisionId, action, amount?, talk?}`. 딜러는 현재 decisionId와 다른 늦은/중복 응답을 폐기한다. `talk`는 이벤트 로그에 테이블 톡으로 표시.

요약 필수 블록: 전 생존자의 (이름, 포지션, 스택, 폴드 여부), 팟(사이드팟 포함), 내 유효 스택, legal 숫자 전부(callAmount·minRaiseTo·maxRaiseTo), decisionId. 상대 스택 없이는 올인·포지션 판단이 불가능하므로 생략할 수 없다.

- 스폰 프롬프트: 페르소나 카드 + 행동 규약 (항상 JSON으로만 응답, 캐릭터 유지, talk는 1문장 이하, 자기 스타일을 직접 발설하지 않기, 매 요약은 자족적이므로 계산은 요약 기준으로).
- 응답 파싱 실패 또는 불법 액션 → 1회 재요청 → 그래도 실패하면 `--force-default` (게임은 절대 멈추지 않는다). AI 결정 wall-clock 한도: 60초 무응답 → 1회 재요청(30초 한도) → `--force-default`. 사용자 대기만 무제한이다.
- 버스트 시: 작별 멘트 한 줄 요청(최선 노력, 20초 한도) 후 실패해도 즉시 퇴장 처리 (에이전트 종료).

## 8. 코칭

### 핸드별 피드백 (코치 패널)

핸드 종료마다 딜러가 `hand <n> --redacted`(사용자 관점에서 공개된 정보만)를 보고 사용자의 주요 결정 1~2개에 1~2줄 코멘트. 팟 오즈·포지션·레인지 개념을 실제 수치와 함께 사용. **공정성 규칙: 핸드 중 공개되지 않은 상대 홀카드는 절대 사용하지 않는다**. 이 규칙은 코치 호출의 입력 격리로 보장한다: 핸드별 코칭은 딜러 컨텍스트에서 직접 쓰지 않고, **redacted 핸드 JSON + 공개 집계 통계(stats) + 직전 게임 연습 포커스 + coach-meta(과폴드 코멘트 기사용 여부)를 입력으로 받는 격리된 1회성 코치 서브에이전트**가 생성하며 딜러는 그 출력을 게시만 한다(딜러 컨텍스트는 전 패를 이미 보았으므로 스스로 쓰면 공정성을 보장할 수 없다). `view --for user`와 public 이벤트에는 아키타입·스타일 정보가 포함되지 않는다. 사용자가 프리플랍에서 접은 핸드는 코멘트를 생략한다(프리플랍 폴드 자체가 주목할 결정인 경우만 예외). 또한 표본 12핸드 이상에서 VPIP가 12% 미만이면(과폴드 누수) 세션 중 1회에 한해 코멘트를 허용한다.

### 종합 리뷰 (게임 종료 시)

전체 핸드 아카이브(비공개 정보 포함)와 `stats` 기반:

평가 규율: 각 결정의 평가는 **결정 시점에 사용자가 볼 수 있었던 정보만으로**(팟 오즈·포지션·상대 액션·레인지 추정) 과정의 질을 먼저 판정하고, 상대의 실제 홀카드와 결과는 별도의 '결과 확인' 절에서만 언급한다. 결과가 좋았다는 이유로 나쁜 과정을 칭찬하거나, 결과가 나빴다는 이유로 좋은 과정을 비난하지 않는다(결과 편향 금지).

이를 보장하기 위해 종합 리뷰도 2단계로 생성한다: ① 격리 evaluator가 결정 시점 redacted 트레이스 + 공개 통계만으로 과정 평가를 먼저 산출하고, ② 종합자가 그 위에 결과 확인·AI 스타일 공개를 덧붙인다.

1. 내 성향 통계: VPIP, PFR, 공격성, 쇼다운 승률 + 해석
2. 결정적 핸드 2~3개 리플레이 분석 (이때는 접힌 패 포함 전체 공개)
3. 각 AI의 실제 아키타입 공개 + 내가 잘/못 읽은 부분
4. 다음 게임에서 연습할 것 1~2가지

VPIP = 자발적으로 프리플랍에 칩을 넣은 핸드 비율(블라인드 강제 제외), PFR = 프리플랍 레이즈 핸드 비율, AF = (벳+레이즈 횟수)/콜 횟수, 쇼다운 승률 = 쇼다운 도달 핸드 중 승리 비율. 표본이 30핸드 미만이면 리뷰에 '참고용'으로 표기.

`start-game`은 `game/review.md`(직전 게임 종합 리뷰)가 있으면 그 '연습할 것' 항목을 읽어 이번 게임 코치의 관찰 포커스로 삼는다.

UI 리뷰 오버레이로 표시하고, `game/review.md`로도 저장.

## 9. 크로스 에이전트 스킬 (`.agents/`)

사용자는 Claude Code · Grok Build · Codex 세 호스트를 사용한다. 스킬 정본은 호스트 중립 위치에 둔다.

```
.agents/skills/start-game/SKILL.md   ← 정본 (SSOT)
.claude/skills/start-game            ← 정본 디렉토리로의 심볼릭 링크
<codex 스킬 경로 또는 AGENTS.md 포인터> ← 구현 시 확정
<grok 스킬 경로>/start-game           ← 심볼릭 링크 (경로는 구현 시 확인)
```

- SKILL.md 본문은 호스트 중립으로 작성: 게임 루프·엔진 CLI·서버 API는 공통이고, "플레이어 에이전트 스폰" 단계만 **호스트 어댑테이션 절**로 분리한다 — **정본 게임 런타임은 Claude Code**(지속 에이전트 = 접근안 A 그대로)다. Codex·Grok 스킬 경로는 **문서화된 저하 모드(degraded mode)**로: 결정 시점마다 페르소나 카드 + 상황 요약으로 1회성 에이전트를 띄우며, 핸드 간 캐릭터 기억이 페르소나 카드 수준으로 제한되고 결정 지연이 커짐을 스킬 문서에 명시한다. 저하 모드는 접근안 A를 대체하지 않는다.
- 구현 시 검증 항목: ① Claude Code가 심볼릭 링크된 프로젝트 스킬을 인식하는지 (안 되면 `.claude/skills/start-game/SKILL.md`를 정본을 참조하는 얇은 래퍼로), ② Codex가 `.agents/skills`를 네이티브 인식하는지 (안 되면 AGENTS.md 참조 또는 심볼릭 링크 브리지), ③ grok의 프로젝트 스킬 경로.

스킬 사용법: `/start-game [AI수 1~8]` (옵션 `--stack N`, `--level-every N`), `/start-game resume`(중단 게임 재개 — 상태 파일에서 복원, 에이전트 재스폰 후 상황 브리핑).

**v1 범위**: 게임 루프 구현과 테스트는 Claude Code(접근안 A)만 필수다. Codex·Grok은 스킬 링크 설치와 저하 모드 주의사항 문서화까지가 v1 범위이며, 저하 모드 런타임 분기 구현은 후속이다.

## 10. 신뢰성·복구

- 에이전트 무응답/깨진 응답: 1회 재시도 → `--force-default`. 게임은 멈추지 않는다.
- 서버 다운: 재기동하면 딜러가 마지막 `view`를 다시 게시. 브라우저는 자동 재접속.
- 딜러 세션 컨텍스트 요약: 상태는 전부 파일에 있으므로 §3의 재진입 체크리스트(health → legal → view 재게시 → 대기/전송)로 그대로 재개.
- 중단된 게임: `/start-game resume`. 에이전트 기억은 리셋되지만(재스폰) 페르소나는 `players.json`에서 복원되고 게임 상태는 이어진다.
- 사용자 자리 비움: long-poll 타임아웃을 무한 반복하며 대기 (게임에 시간제한 없음).

## 11. 테스트 전략

- **엔진 단위 테스트에 집중** (`node --test`, 의존성 0 유지):
  - 핸드 평가기: 족보 전 등급 판별, 킥커 비교, 휠 스트레이트(A-2-3-4-5), 스틸 휠 플러시, 동점 스플릿
  - 사이드팟: 3인 이상 올인 시나리오, 홀수 칩 분배
  - 버튼/블라인드 로테이션: 3인 이상 + 헤즈업 특례, 탈락자 발생 시 버튼 이동
  - 베팅 규칙: 미니멈 레이즈, 언더 레이즈 올인의 재오픈 금지, 체크-레이즈
  - 상태 전이: 스트리트 자동 진행, 올인 런아웃, 강제 기본 액션
  - 액션 슬롯: 더블클릭·낡은 decisionId·소비 후 잔량 없음
  - `--expect-version` 불일치 거부, 오류 시 상태 무변경 보장
  - 이벤트 visibility: public 이벤트·view에 상대 홀카드·덱·아키타입이 없음(고정 픽스처 검사)
  - handOver/gameOver: 사용자 버스트·AI 전원 탈락·동시 버스트·종료 후 new-hand 거부
  - init의 활성 게임 거부, resume의 lock 생존 거절, 핸드 아카이브-state 정합 자가검사
  - 레벨업 오프바이원(N핸드 완료 후 다음 new-hand의 블라인드 포스팅 전 적용)
- 서버: 스모크 테스트 (publish → SSE 수신, action → wait-action 왕복)
  - 토큰 없는 요청 거부, 스냅샷 revision 복원, SSE 재접속 시 로그·코치 복원
  - 코칭 격리: 코치 입력 JSON에 비공개 홀카드 부재(입력 스냅샷 검사)
- UI·전체 흐름: 수동 확인 + 브라우저 자동화 도구로 스모크

## 12. 범위 외 (YAGNI)

앤티, 리바이/애드온, 멀티테이블, 토너먼트 순위표, 사운드, 고급 애니메이션, 모바일 최적화, 영어 UI, 실시간 힌트 버튼, 데이터베이스(파일로 충분), 관전자 모드, 핸드 리플레이어 UI.

## 13. 리스크

| 리스크 | 대응 |
|---|---|
| 심볼릭 링크 스킬 미인식 (호스트별) | §9의 검증 항목. 폴백: 얇은 래퍼 파일 |
| 긴 게임의 토큰 소모 | 압축 JSON 프로토콜(요청 수백 토큰, 응답 한 줄), 자족적 요약으로 에이전트 컨텍스트 성장 억제 |
| AI 결정 지연으로 처지는 느낌 | UI에 "OO 생각 중…" 표시, 기본 4인 테이블 |
| LLM의 칩 계산 오류 | 전 규칙 엔진 판정. 딜러·에이전트는 계산 결과를 신뢰만 함 |
| SSE 끊김·새로고침 | snapshot 복구 + 자동 재접속 |
| 지속 에이전트 응답 대기의 타임아웃 메커니즘이 호스트에 없을 수 있음 | 딜러 스킬의 폴링 규약(60s/30s 한도)으로 구현하고, 구현 시 실측 검증 |
| Node 내장 http의 장시간 SSE·long-poll 소켓 타임아웃 | server.timeout/keepAliveTimeout 설정과 heartbeat로 해결, 구현 시 실측 검증 |

## 14. 구현 검증으로의 이월

문서 리뷰 수렴 규칙에 따라, 아래 항목은 산문으로 더 다듬지 않고 구현 단계의 기계 검증(테스트·리허설)으로 이월한다.

| 항목 | 상태 |
|---|---|
| 핸드 종료 후 부수효과(코칭·작별 멘트)의 중복/누락 방지 | 경량 멱등화로 처리: coach 노트에 handNo를 붙이고, 재진입 시 마지막 coach handNo를 확인해 스킵 |
| 에이전트 응답 타임아웃의 호스트 프리미티브 | 구현 시 실측 (§13 리스크) — 워치독 규약은 스킬 문서에 |
| 이중 딜러 세션 방어 강화 | 수용 리스크: 단일 사용자 머신 전제. 엔진 mutation lock이 상태 훼손은 차단 |
| SSE·long-poll 소켓 keepalive 동작 | 구현 시 실측 (§13 리스크) |
| 호스트별 스킬 경로·링크 인식 확정 | 구현 플랜의 선행 태스크로 이관 |
| 명령별 operationId 전면 멱등 체계 | 기각: mutation lock + expect-version + 안정 decisionId로 충분 |
| dealerToken/playerToken 이원화 | 기각: 로컬 단일 사용자 위협모델. 원격 접속을 지원하게 되면 재검토 |
| 사이드팟·베팅 엣지케이스 전수 | 원래 계획대로 §11 단위 테스트가 검증 |
