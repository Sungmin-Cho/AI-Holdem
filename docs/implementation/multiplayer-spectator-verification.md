# 멀티플레이 관전 구현·검증 기록

2026-09-20 · 브랜치 `feat/multiplayer-spectator`

설계·계획·설계 검토 문서는 구현 승인 이전 기록이다. 이후 사용자가 이 워크트리에서 구현, 실제 플레이 검증, PR 및 병합까지 승인해 구현했다.

## 구현 결과

- 게임 진행/일시정지 중 같은 참가 링크로 들어온 사람은 좌석과 별개인 관전자로 입장한다.
- 관전자는 현재 핸드의 사람·AI·폴드한 사람의 홀카드를 실시간으로 본다. 미래 덱, 개인 코칭·학습 정보는 제외한다.
- 토너먼트 정산으로 탈락이 확정된 참가자와 호스트는 자동 관전한다. 올인 중 스택 0은 탈락으로 취급하지 않는다. 마지막 인간 탈락 종료 규칙은 유지한다.
- 늦게 온 관전자는 다음 게임에도 관전하며 열린 로비에서 직접 참가 신청한다. 기존 탈락 참가자의 좌석 자격은 유지한다.
- 관전자는 행동할 수 없고, 호스트의 게임 관리 권한은 관전 전환과 별개로 유지된다.
- 호스트는 관전자를 내보내거나 참가 코드를 바꿀 수 있다. 열린 로비에서는 기존 참가자의 재입장 링크 발급과 좌석 비우기도 가능하다.

지인 간 신뢰를 전제로 한다. 플레이어가 별도 신원으로 관전하는 것을 막지 않는다. 관전 전용 정원 20명은 좌석에서 전환된 탈락자를 제외한다. 퇴장한 탈락자의 고정 명단은 복구를 위해 보존하며, 호스트가 다음 게임 전에 재입장시키거나 좌석을 비운다.

## 독립 검토와 수정

최초 CLI 검토의 형식 오류와 실행 실패는 승인으로 계산하지 않았다. 이후 Claude 1명·독립 Codex 2명의 교차 검토와 추가 독립 Codex 검토를 수행했다. 리뷰용 사본은 변경 파일의 SHA-256을 원본과 대조했고, 각 리뷰 전후 읽기 전용 지문을 확인했다. 저장소의 기존 추적 symlink를 변경하지 않기 위해 사본에서만 `core.symlinks=false`를 사용했다.

검토에서 확인한 사항은 다음과 같이 반영했다.

| 발견 | 조치와 확인 |
| --- | --- |
| 탈락 호스트의 내부 복구 probe가 관전 응답에 묶임 | 비공개 loop probe 계약 분리, 공개 프록시 헤더 위조 차단 테스트 |
| 참가자 상태 조회가 큰 snapshot을 반복 파싱 | 파일 identity 기반 파싱 캐시와 반복 조회 테스트 |
| 탈락 후 퇴장자의 호스트 복귀/제거 UI 부족 | 재입장 링크·좌석 비우기 UI 및 실제 브라우저 퇴장→재입장 검증 |
| UI 저장 뒤 실패하면 기존 guest SSE 갱신 누락 | 재조정 완료 시 seat-scoped snapshot 전달, 두 post-commit 오류 지점 RED→GREEN |
| 느린 참가 신청 중 토큰 재발급을 우회 | body 수신 후 재인증, 실제 room/server partial-body 요청 200→401 RED→GREEN |
| 앱이 UI 파일만 보고 게시 실패 후보의 탈락을 확정 | view anchor의 publishId를 loop의 성공 확인과 대조, 역할·퇴장 권한 두 오류 지점 RED→GREEN |
| 복구 검증 실패 후 기존 메모리 관전 카드가 남음 | projection과 anchor를 명시적으로 null 처리, 거절된/뷰 없는 재시도 200→503 RED→GREEN |
| guest 복구 snapshot이 행동 컨트롤러에 전달되지 않음 | 실제 SSE 어댑터가 새 view/revision을 observe하도록 하고 실행형 어댑터 테스트 추가 |

마지막 독립 검토는 수정 전 stale projection을 지적했다. 이후 null 초기화 패치와 실패 재현 테스트로 수정 확인했다. 수정 전 리뷰의 APPROVE를 수정 후 전체 코드의 새 독립 승인으로 재사용하지 않는다.

## 검증 범위

- 전체 `npm run test:ci`는 순차 실행했다. 최초 2,736개 중 3개 실패를 보존하고 원인을 수정한 뒤, 다음 전체 실행 2,737개 모두 통과했다.
- 최초 실패 원인: 순수 view import의 정적 경계 allowlist, 기존 Grok inspect CLI 테스트의 잘못된 argv 기대값, publish 복구 중 기존 player snapshot 계약. Grok 실패는 변경 없는 기준 코드에서도 재현했다.
- 마지막 보완 후 관련 96개 테스트 통과: 관전 room/projection/client, participant API, relay seat scoping, server, lobby markup, architecture boundaries.
- 실제 앱과 독립 브라우저의 호스트·guest 2명·늦은 관전자 세션에서 UI로 플레이했다. 고정 덱 주입, 엔진 상태 변조, 직접 액션 API 전송 없이 호스트/guest 탈락 경로를 확인했다.
- 전체 카드·폴드 카드·일반 참가자 카드 비공개·조작 차단·재접속·390px 모바일·결과·다음 게임 관전 유지·직접 참가 신청·새 게임 카드 초기화를 검증했다.
- guest 탈락 후 퇴장→호스트 링크 재발급→재입장과 호스트 좌석 제거도 실제 브라우저에서 확인했다.
- 기존 multiplayer, lobby, UI presentation journeys도 통과했다. 실제 사용자 `game/` 트리의 hash 불변과 테스트 소유 서비스·브라우저 정리를 확인했다.
- 최종 전체 재실행 결과와 Linux/Windows CI의 최종 상태는 PR 검증 기록에 남긴다. 설치되지 않은 ESLint/Stryker를 실행했다고 주장하지 않는다.
- 첫 PR CI의 Windows Node 20/22 `rest`에서 관전 fixture 13개가 `state.json` rename `EPERM`으로 실패했다. 같은 프로세스의 비동기 hint 초기화 reader가 닫히기 전에 동기식 엔진 쓰기가 event loop를 막는 fixture 경쟁이었다. host snapshot의 초기화 완료 응답을 기다리도록 수정했으며, 열린 reader를 추적하는 회귀 테스트에서 수정 전 1개 잔존→수정 후 0개를 확인했다. 원자적 저장·보안 판정은 변경하지 않았고 두 버전의 원본 실패 로그를 보존했다. Windows 실제 수정 검증은 후속 CI 결과로 판단한다.

로컬 원본 로그·스크린샷·독립 리뷰 근거: `/tmp/holdem-spectator-validation.pRpm4j/`. PR의 UI browser artifact에는 새 관전 journey 결과가 포함된다.

## 호환성

room schema 1은 기존 토큰과 좌석을 보존하며 schema 2로 상향 변환한다. 알 수 없는 schema/role은 거절한다. anchor가 없는 구 snapshot은 검증된 현재 상태를 재게시하기 전까지 전체 카드를 제공하지 않는다. schema 2를 기록한 세션을 구버전 reader로 다운그레이드하지 않는다.
