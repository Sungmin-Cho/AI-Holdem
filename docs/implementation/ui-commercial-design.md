# UI 상품성 개선 설계

날짜: 2026-09-11 · 기준 HEAD: `161cd7a` · 작성 범위: 설계와 구현 계획.
관련 문서: [구현 계획](ui-commercial-plan.md), [검토 기록](ui-commercial-review.md), [시각 시안](ui-commercial-preview.html).

## 1. 목표와 범위

BB 환산, 탈락 플레이어 식별, 로비부터 게임·복기까지 일관된 디자인, 플레이를 방해하는 UX 문제 개선을 하나의 UI 작업으로 진행한다. 기능을 찾기 쉽고 숫자를 읽기 쉬운 연습 제품이 목표다. 실제 출시 적합성이나 학습 효과를 문서/스크린샷으로 보증하지 않는다.

이번 단계에서는 제품 코드를 변경하지 않는다. 구현 시에도 엔진 베팅·정산·탈락 규칙, 게임 제어·재시도 프로토콜, 저장 포맷·학습 채점은 유지한다. 공개 view에 상태 필드를 추가하고 프런트엔드에서 표현을 개선한다. 프레임워크 전환, 계정/결제, 멀티플레이, 서버 호스팅, 사운드·화려한 애니메이션은 범위 밖이다. 독립 학습실은 공통 시각 토큰·기본 컨트롤만 적용하며 드릴 구조 개편은 별도다.

## 3. 금액 표시 계약

### 3.1 기준과 표현

`BB = chips / bigBlind`. 칩·블라인드는 유한 안전 정수이며 BB 분모는 양수여야 한다. invalid/missing amount는 `—`, 유효 칩 + invalid/missing BB는 칩만 표시하고 보조에 `BB 기준 없음`을 제공한다. 숫자 문자열·null을 암묵적으로 0으로 바꾸지 않는다.

기본은 **BB 주표기 / 칩 보조표기**다. 상단의 `BB 중심 / 칩 중심`으로 우선순위만 바꾸며 다른 단위는 유지한다. 핵심 숫자에 항상 단위를 쓴다. 5,000칩, BB=50 → `100 BB` + `5,000 칩`; 125칩 → `2.5 BB`; 1칩, BB=200 → `<0.01 BB` + `1 칩`. 0은 `0 BB`, 음수의 작은 값은 `−<0.01 BB`. 0이 아닌 절댓값의 0.01 미만 여부를 반올림 전에 판단한다. 소수는 최대 두 자리, 끝 0 생략, 반올림한 근사값에는 `≈` 표시. 임의 K/M 축약은 사용하지 않는다. 손익은 +/− 기호와 텍스트로 구분하고 색만 사용하지 않는다.

BB 우선순위 선택은 브라우저 localStorage의 `holdem.display-unit.v1`에 `bb|chips`만 저장한다. 읽기·쓰기가 막혀도 기본값으로 동작하며 게임/학습 데이터나 인증값은 저장하지 않는다. 입력란은 항상 `레이즈 총액 (칩)`이다. 단위 전환은 입력 문자열·커서·raiseTo·decisionId·제출 payload를 바꾸지 않는다. 같은 origin의 세션 사이에서만 표시 취향을 재사용한다. 앱 재기동의 포트 변경이나 standalone/app 간에는 취향 공유를 보장하지 않으며 기본값으로 동작한다.

| 표면 | BB 분모와 범위 |
|---|---|
| 좌석 스택·현재 베팅·팟·콜·레이즈 미리보기/합법 범위 | 해당 view의 `blinds[1]` |
| 직전 완료 핸드를 보여주는 테이블 | viewFor가 제공하는 lastHand.blinds, 다음 레벨 분모 금지 |
| 핸드 복기 액션/팟 | 해당 handReplay의 `blinds[1]`, 현재 테이블 분모 사용 금지 |
| 이벤트 로그의 구조화 금액 | hand_start의 handNo/blinds로 그룹 연결. 해당 그룹 분모 없으면 칩만 |
| 캐시 세션 순손익 | 고정 BB가 제공된 cash-training view. `누적 손익` 레이블 |
| 토너먼트 세션 순손익 | 현재처럼 `—`를 계속 노출하지 않고 항목 숨김. 스택을 누적 손익으로 해석하지 않음 |
| 블라인드/설정 | `25 / 50 칩 · 1 BB = 50 칩`. 시작 스택 입력에 즉시 칩/BB 환산 보조 |
| 코치·리뷰 본문·export | 원문과 구조 보존. 임의 텍스트 숫자 치환 금지 |
| 학습 카드/힌트 | 기존 의미 있는 BB 및 범위 표기 보존. 새 formatter로 숫자 의미를 바꾸지 않음 |

칩 값은 엔진 정수 그대로 유지한다. BB는 표시 전용이며 직접 BB 입력은 이번 범위에 넣지 않는다. slider/preset은 기존 clampRaiseTo/potRaiseTo/bbRaiseTo와 합법 범위를 그대로 사용한다. 버튼은 `콜 2 BB / 100 칩`, `총액 레이즈 6 BB / 300 칩`처럼 추가 콜 금액과 스트리트 총액을 구분한다. `추가 투입` 보조값을 보여줄 경우 `raiseTo − 내 현재 bet`이며 음수/불명은 표시하지 않는다.

입력 UX 보완: 현재 app.js의 비숫자 제거는 `2.5`를 `25`, `-5`를 `5`로 만들 수 있다. 새 UI는 ASCII 정수 또는 올바른 세 자리 쉼표 표기(`1,250`)만 받고 앞뒤 공백만 제거한다. 빈 값·소수·지수·부호·잘못된 쉼표는 오류로 표시하며 레이즈 제출을 막는다. 마지막 유효 raiseTo를 잘못된 입력 대신 몰래 제출하지 않는다. 유효 정수의 범위 보정은 기존 clamp 정책을 유지하되 보정값을 입력/미리보기에 명시한다. 새 decision은 기존 adoptDecision 규칙대로 초기화하고 단위 토글은 오류 입력을 보존한다. 같은 decision의 SSE/snapshot 재도장은 focus 유무와 관계없이 오류 텍스트/오류 상태를 보존한다. slider·preset·ArrowUp/Down 선택은 사용자의 명시적 유효 금액 선택이므로 입력을 대체하고 오류를 해제한다. 짧은 올인 전용 버튼도 기존 합법 금액을 명시 선택하는 경로로 동작한다. 다른 자동 paint/write와 재focus는 오류를 해제하지 않는다. focus는 현재 텍스트가 유효 raiseTo와 동등할 때만 정규화하며 사용자가 편집한 텍스트는 보존한다. 범위 밖 유효 정수는 입력 중 경고를 표시하고 blur/Enter에서 clamp한 실제 칩을 명시한다. 레이즈 click 핸들러도 즉시 재파싱하며 구문 오류는 POST를 거부한다. 범위 보정이 그 순간 처음 필요하다면 값만 보정해 보여주고 다시 명시적으로 레이즈를 눌렀을 때 제출한다(disabled나 blur 이벤트 순서에만 의존하지 않음). ArrowUp/Down은 오류 상태이면 마지막 유효 raiseTo를 기준으로 기존 BB step/clamp를 적용해 새 유효 입력으로 대체한다. 007은 정수7로 허용하고 전각 숫자는 구문 오류다. clamp가 값을 바꾸면 pendingCorrection=true를 기록한다(blur에서 보정되어도 유지). 유효 상태의 레이즈 click이 이 플래그를 만나면 이를 해제하고 제출하지 않는다. 다음 명시 click에서만 제출할 수 있다. 사용자 편집·slider/preset/화살표·새 decision도 이 플래그를 해제하며, 뒤이어 clamp가 다시 값을 바꾸면 재설정한다. SSE/refocus/단위 토글은 플래그를 보존하고 pending receipt 동안에는 소비하지 않는다. 구문 오류+Enter는 오류 유지, 제출·정규화 없음이다. Enter는 기존처럼 검증/커밋만 하며 액션을 제출하지 않는다. pending receipt가 있으면 모든 금액 선택/제출은 기존 controller의 잠금이 우선한다. fold/check/call은 별도 기존 합법 조건에 따른다.

### 3.2 모바일 밀도

좌석 BB/칩은 두 줄을 기본으로 하되 촘촘한 테이블의 보조 칩은 좌석 상세 패널로 이동할 수 있다. 그 경우 주표기 숫자와 단위, 이름, 상태는 항상 보이며 키보드/터치로 다른 단위를 확인 가능해야 한다. hover/title만으로 정보를 제공하지 않는다. 팟·내 스택·콜/레이즈는 모바일에서도 양 단위를 바로 읽을 수 있게 유지한다.

## 4. 탈락과 핸드 상태

### 4.1 데이터 계약

`publicSeat`에 `out: Boolean(seat.out)`을 추가하고 `viewFor`에 `handInProgress: Boolean(state.hand && state.phase === 'in_hand')`를 추가한다. out은 정산 후 엔진이 확정한 값이다. stack=0, folded, allIn, toAct 부재로 탈락을 추론하지 않는다. 기존 원본 state/history를 재작성하지 않는다. view 변경은 기존 producer → publish → ui-snapshot → snapshot/SSE → app proxy → 렌더에 전달되는 additive 변화이며 allowlist·검증·fixture의 정확 일치 테스트를 함께 확인한다.

구버전 view에서 필드 부재는 `unknown`이다. 새 브라우저가 접속해도 탈락/생존 수를 추측하지 않으며 명시된 탈락 좌석만 뱃지로 표시한다. 토너먼트(legacy mode 부재 포함)이고 모든 좌석 out이 boolean일 때만 `남은 인원 N / 전체 M`을 표시한다. cash-training은 `참가자 M명`으로 표시하고 남은 인원/탈락 개념을 사용하지 않는다. 누락 snapshot을 보완하려고 상태 파일을 읽거나 마이그레이션하지 않는다. 정상 새 publish 이후 정확한 상태가 표시된다. handInProgress 부재에서는 기존 공개 allIn/folded 표현을 유지하되 새 완료 전용 표시는 생략한다.

### 4.2 상태와 공개 카드

| 상태 | 표현 |
|---|---|
| tournament + out=true | `탈락` 최우선, 이름/자리 유지, 능동 차례 강조·애니메이션·현재 베팅 뱃지 제거 |
| out=false + 진행 중 allIn | `올인`, 0칩이어도 생존 수에 포함 |
| out=false + 진행 중 folded | `폴드`, 다음 핸드 정상 복귀 |
| 정상 내 차례 | 고대비 외곽선 + `행동 중`/`내 차례` 텍스트, 가짜 남은 시간 없음 |
| 핸드 종료, out=false | 이전 allIn/folded를 현재 상태처럼 남기지 않음 |
| cash 핸드 종료 후 스택 reset | handInProgress=false이며 gameOver=false인 핸드 간 경계에서만 `다음 핸드를 위해 스택을 복원했습니다` 안내(이미 반영된 스택). 누적 손익과 스택 분리. 해당 완료 핸드 정보는 기존 복기/기록에서 확인하며 새 endStacks를 view에 추가하지 않는다. sessionNet이 없으면 손익은 `—`로 표시하며 0을 추정하지 않음 |
| cash 마지막 핸드 또는 종료 | 스택 복원을 약속하지 않음. engine의 최종 스택/누적 손익을 표시 |

탈락 좌석에 새 카드 뒷면을 만들지 않는다. 좌석 reveal 입력은 기존 revealedCards 경로의 공개 로그에서, hand_start.handNo===view.handNo인 그룹의 showdown.reveals(플레이어→공개 cards)와 showdown.mucks(Set)다. 사용자 카드는 view.myCards만 사용한다. 해당 그룹/공개 소스가 없으면 카드 영역을 비우고 실제 mucks에 있는 플레이어만 머크로 표시한다. handReplay의 replayReveal=all을 테이블 reveal로 재사용하지 않는다. handInProgress=false인 완료 화면에서는 생존 좌석의 비공개 카드 뒷면도 제거하고 공개 카드/머크 텍스트만 남긴다. 다만 **지금 보고 있는 완료 핸드에서 이미 공개된** 쇼다운/사용자 카드는 탈락 직후에도 기존 reveal 권한대로 보여준다. 다음 핸드에서는 사라진다. 예전 핸드의 공개 카드를 현재 자리로 끌어오거나 비공개 hole을 읽지 않는다. 딜러 D는 진행 중 비탈락 좌석에만 표시하고 완료 핸드의 버튼 정보는 복기 헤더로 확인한다. 최종 순위·탈락 순서/핸드 번호는 별도 근거가 없으므로 만들지 않는다. 동시 탈락은 같은 게시에서 함께 갱신한다. 본인이 탈락해도 리뷰·학습 진입은 유지한다.

자리 순서는 초기 seat 배열과 hero anchor를 유지한다. 탈락자를 필터링해 테이블을 회전/재배치하지 않는다. 참가자 목록은 별도 탭으로 제공하고 `플레이 중 / 올인 / 폴드 / 탈락 / 상태 확인 불가`를 텍스트와 칩/BB로 읽게 한다. 접근성 announce는 out=false→true 변화에만 1회, 새 snapshot 재연결로 탈락 토스트를 반복하지 않는다.

## 5. 화면 디자인

### 5.1 시각 체계

방향: 조용한 포커 연습실. 배경 `#0B1118`, 표면 `#131D29`, 높은 표면 `#1B2938`, 본문 `#EDF3F8`, 보조 `#A9B8C8`, 강조 에메랄드 `#5BDFB0`, 금색 `#E5BF75`, 위험 `#F18A8A`. 펠트는 낮은 채도의 깊은 청록, 레일은 얇게 만든다. 실제 대비는 구현 때 측정한다.

공통 `design-tokens.css`를 로비·테이블·학습실에 적용한다. 기존 DOM ID와 엔진 연동을 보존하며 vanilla ES module을 유지한다. Google Fonts 외부 링크/preconnect를 제거하고 한국어/시스템 폰트 스택을 사용하며 숫자는 tabular-nums. 본문 14–16px, 보조 12–13px, 주요 BB 18–24px를 기준으로 한다. 모바일 좌석 핵심 숫자는 12px 미만으로 축소하지 않는다. spacing 4/8/12/16/24/32, panel radius 16, control radius 10. 클릭 가능한 컨트롤은 최소 44×44 CSS px를 목표/승인 기준으로 둔다.

### 5.2 정보 구조

| 화면 | 구성 |
|---|---|
| 로비 | 브랜드·연결 상태 / 모드 선택 카드 2개 / 인원과 시작 스택·핸드 수 요약 / 상세 설정 / 게임 시작 |
| 상세 설정 | 게임 규칙, 연습 보조, AI 동작으로 구획. LLM 대기 설정은 LLM일 때만 표시하고 사용자에게 초·분으로 설명하되 API 값은 기존 ms |
| 데스크톱 게임 | 앱 메뉴 헤더 / 테이블 문맥(핸드·블라인드·남은 인원·단위) / 테이블 / 내 스택과 액션 영역 / 우측 로그·코치·학습·참가자 |
| 모바일 게임 | 한 줄 앱 헤더 / 접이식 상세 문맥 / 세로형 테이블 / 내 카드·스택 / 하단 액션 / 하단 보조 탭 |

로비의 설정을 모두 숨기지 않는다. 시작 전 `토너먼트 · 총 9명 · 100 BB · 25/50 칩`처럼 핵심 설정 요약이 보인다. 유리한 딜·행동 전 힌트·비표준 공개 설정은 활성 상태를 요약에서 확인하게 한다. 지원하지 않는 학습 점수를 성과처럼 표현하지 않는다.

앱 iframe 구조를 유지한다. 앱 헤더는 메뉴·앱 상태, iframe의 문맥 바는 게임 정보만 담당한다. iframe에서 브랜드/학습 진입의 중복을 줄이되 standalone에는 자체 진입을 유지한다. 모바일 앱 페이지는 flex/grid로 헤더 실측 높이를 반영하고 고정 `100dvh - 80px`에 의존하지 않는다. 화면 축소 시 iframe 내부 스크롤을 허용하며 액션 영역은 iframe 내에서만 sticky다. safe-area와 키보드를 고려하고 카드/합법 범위를 덮지 않게 여백을 확보한다.

좌석 배치는 데스크톱 기존 oval 계열을 개선하고 모바일(≤600px)에서는 명시적 2–9인 레이아웃으로 전환한다. 9인은 양쪽 3명 + 상단 2명 + 하단 hero로 배치하고 다른 인원은 아래 슬롯 표를 정본으로 삼으며 좌석 너비와 행 간격을 확보한다. 화면 너비에 따라 임의 순서 변경하지 않는다. 601–1023px는 테이블 아래 보조 패널, 1024px 이상은 우측 패널(320–380px)이다. 시안은 방향/배치의 예시이며 실제 상태별 합격은 브라우저 gate로 결정한다.

모바일 배치 순서는 hero 다음 좌석부터 왼쪽 아래→위→오른쪽 위→아래로 대응한다. 기준 슬롯은 H(50%,100%), L3(0%,78%), L2(0%,54%), L1(0%,29%), T1(28%,4%), T2(72%,4%), TC(50%,4%), R1(100%,29%), R2(100%,54%), R3(100%,78%)이다. 테이블 내부 중심 좌표이며 외곽 padding은 플레이트 반폭+최소 여백을 확보한다. 칩 중심/긴 숫자로 충돌하면 테이블 너비를 넘기지 않고 행 높이·상세 패널을 조정한다.

시스템 숫자 스택은 `Arial, ui-monospace, monospace`를 우선하고 한국어 본문은 시스템 한글 폰트로 구분한다. 숫자 셀의 최소 폭을 확보해 tabular-nums 지원 여부에만 의존하지 않는다. 시안의 Inter는 제품 필수 의존성으로 채택하지 않는다.

## 6. 추가 개선의 확정 범위

1. **팟 표시**: `합계`는 view.pots amount 합산 1회(legal.potTotal이 있으면 정합성 확인). 진행 중에는 allIn/eligible 수와 무관하게 `현재 베팅 포함 총액`만 표시한다. 완료 핸드(handInProgress=false)의 팟이 여러 개일 때만 엔진이 정산한 `메인 / 사이드 1 / 사이드 2` 상세를 원래 순서로 표시한다. eligible이 0/1명인 진행 중 층으로 응답 대기·반환 예정액을 추정하지 않는다. raw 합과 legal.potTotal 불일치 시 상세를 숨기고 `팟 정보 확인 중`으로 표시한다(추가 베팅 자동 해제/전송 없음). 정상 상태 갱신에서 회복한다. 완료 화면(handInProgress=false, handNo>0)의 pots 부재/빈 배열/잘못된 amount는 `팟 정보 없음`으로 표시하며 0으로 변환하지 않는다. 시작 전에는 팟 영역을 숨긴다. engine/hand.js:593은 실제 정산 potRecords를 lastHand.pots에 저장하므로 정상 완료 fixture에서 그 전달을 검증한다. 상대 차례처럼 legal이 없는 경우 교차 대조를 했다고 주장하지 않고 유효 raw 합만 표시한다. 기존 정산 숫자는 바꾸지 않는다. 구버전 handInProgress 부재에서는 항상 합계만으로 보수적 표시.
2. **읽기 지속성**: 로그는 기존 hand/event 식별자와 append 순서를 활용한다. 기존 행을 매번 지우지 않고 끝에 있던 사용자만 자동 스크롤한다. 과거 읽는 중이면 `새 이벤트 N개` 버튼 제공. coach는 handNo, training은 기존 evaluationId/detailSha256 키로 갱신한다. 단위 전환·SSE 갱신이 열림/선택/스크롤/포커스를 초기화하지 않는다.
3. **접근성**: 탭 roving tabindex+좌우/Home/End, dialog 열기 포커스·Tab 격리·Escape·닫기 원래 trigger 복원. 모달은 한 번에 하나, 사용자의 명시적 열기로 테이블 모달끼리는 교체한다. 복기/좌석 상세를 읽는 중 도착한 자동 종합 리뷰는 뱃지로 알리고 닫은 뒤 열도록 보류한다. iframe 모달과 앱 pause dialog가 겹치면 parent native dialog가 우선한다. parent dialog가 열린 동안 iframe의 기존 inert 값과 focus를 보관하고 inert=true로 둔다. 닫을 때 저장된 inert와 최신 paused/playing 상태를 함께 적용하므로 paused 프레임을 활성화하지 않는다. 최신 상태가 허용할 때만 해당 iframe focus를 복원한다. 모달 오픈만으로 pause/resume 명령을 새로 보내지 않는다.
4. **상태 안내**: 연결 복구/액션 접수/결과 확인 중/입력 가능을 기존 controller 상태에서 파생한다. 새 CSS/BB 토글이 disabled를 해제하지 않는다. 무응답 AI에 가짜 카운트다운·자동 폴드 동작을 추가하지 않는다.
5. **읽기·레이아웃**: 코치/학습 안내문은 간결한 요약+자세히 구조. 학습 범위/유리한 딜/기계 피드백 한계는 접근 가능한 곳에 유지. 로그 전체를 aria-live로 매번 읽지 않고 액션/상태 변화만 짧게 announce한다. reduced-motion에서 장식 움직임 제거.

## 7. 수용 기준

- 현재 및 기록 BB가 올바른 분모와 반올림으로 표시되고 단위 전환 뒤 제출 칩 값이 바뀌지 않는다.
- 0칩 올인/폴드/탈락/캐시 reset을 구분하며 동시 탈락, 재연결, 이전 view 누락, 공개 쇼다운 모두 처리한다.
- 2/6/8/9인, 360·390·768·1024·1440 폭 및 낮은 높이 667px에서 가로 스크롤·핵심 좌석 겹침·액션 가림이 없다. 낮은 높이에서는 일반 배율에서도 세로 스크롤을 허용한다. 액션 위치까지 스크롤하면 내 카드·내 스택·현재 팟의 요약과 합법 액션/레이즈 입력을 함께 확인할 수 있어야 한다. 모든 좌석과 액션을 항상 한 화면에 강제로 압축하지 않는다. 200% 확대와 OS 글자 확대 시 필요한 세로 스크롤은 허용한다.
- 팟 합계 보존, 정확한 메인/사이드 구분, 상대 비공개 카드 비노출, 기존 학습 출처/힌트 무효화/액션 receipt 동작을 보존한다.
- 로비 설정→게임→일시정지→복기/리뷰→새 게임→학습실 왕복이 기존 제어 계약대로 동작한다.
- 모달/탭/표시 단위/좌석 상세는 키보드로 사용 가능하고 일반 텍스트 대비 4.5:1, 큰 텍스트/컨트롤 경계 3:1을 측정한다.

## 8. 구현 준비 판단의 범위

필수 제품 선택은 이 문서에서 정한다. 구현 플랜은 파일 경계·의존성·검증·회귀와 rollback을 지정한다. 실제 반응형 측정, 실제 브라우저 동작, CI, 최종 코드 리뷰는 구현 완료 조건이며 이 문서 검토의 통과로 대체하지 않는다.
